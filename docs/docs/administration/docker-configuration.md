The BigBlueButton container images configure themselves at start from environment variables.
Compose only passes the variables on; the same images and variables work with other
orchestrators.

## How configuration works

| Tier | What | Where | Who sets it |
|---|---|---|---|
| 1 | Essential values | `.env` (template: `.env.sample`) | the setup container or the admin |
| 2 | Advanced values with defaults | `.env`, optional | admins with special needs |
| 3 | Override files | mounted at the same paths as on a bare-metal server | admins following the existing BigBlueButton documentation |

- Every value has a format. An image refuses to start when a required value is missing or a
  value does not have its format, and names the variable in its log.
- Derived values (URLs, TURN URIs, per-service settings) are computed by the images. Do not set
  them.
- Set `BBB_FEATURES` only in `.env`, not in the shell, so that the started services and the
  image configuration agree.
- Booleans are `true` or `false`; lists are comma-separated without spaces.

Status of an entry: **draft** (proposal), **pending (networking spikes)** (depends on
measurements of the container networking), **pending (open decision)** (see
[Open decisions](#open-decisions)).

## Open decisions

Questions still open in this draft. Variables they affect have the status "pending (open
decision)".

### postgres-role-passwords

The PostgreSQL roles bbb_core, hasura_app, bbb_hasura and blocknote_app use fixed public passwords upstream, and the bbb_hasura DSN is a literal in the Hasura metadata. Keep the upstream values or generate secrets?

- **(a)** Upstream values, no variables. Simplest, parity with bare metal; any container on the bbb network that reaches postgres can use the roles.
- **(b)** One generated Tier 2 secret per role (POSTGRES_BBB_CORE_PASSWORD, POSTGRES_HASURA_APP_PASSWORD, POSTGRES_BBB_HASURA_PASSWORD, POSTGRES_BLOCKNOTE_PASSWORD). setup generates them, db-init sets them; the graphql image rewrites the metadata DSN before metadata apply. Needs four new fixtures.
- **(c)** One generated secret shared by all application roles (one variable, less isolation).

**Recommendation:** b. db-init recreates the roles on every version change anyway (ADR-14), so generated passwords cost nothing at upgrade time, and admins never see them (Tier 2, generated).

**Affects:** `POSTGRES_BBB_CORE_PASSWORD`, `POSTGRES_HASURA_APP_PASSWORD`, `POSTGRES_BBB_HASURA_PASSWORD`, `POSTGRES_BLOCKNOTE_PASSWORD`

### recording-retention

Upstream published_days deletes the raw data of recordings published more than N days ago; published recordings stay. The contract draft described deleting published recordings. Which semantics and name?

- **(a)** Upstream semantics, renamed RECORDING_RAW_RETENTION_DAYS (default 14); deleting published recordings stays a documented manual recipe, as upstream.
- **(b)** Upstream semantics under the name RECORDING_RETENTION_DAYS.
- **(c)** Two variables: raw-data retention (upstream) and an opt-in published-recording retention (0 = keep forever).

**Recommendation:** a. Same behaviour as bare metal, and the name says what is deleted. A published-recording retention can be added later without breaking anyone.

**Affects:** `RECORDING_RETENTION_DAYS`

### features-mapping

Which settings does each BBB_FEATURES entry change, and where do images read the feature list from (OQ-18: a shell-exported BBB_FEATURES can disagree with COMPOSE_PROFILES)?

- **(a)** Features only switch profiles; images ignore them. bbb-web would still offer recording without the recording services.
- **(b)** Images map features to settings: without recording, bbb-web sets disableRecordingDefault=true and nginx drops the playback locations; with it, upstream defaults. Images read BBB_FEATURES; docs say to set it only in .env, and preflight warns if the shell exports it.
- **(c)** As b, but images read the profile list compose actually used (COMPOSE_PROFILES), pending RB-00.

**Recommendation:** b now (simple, testable with render-only), revisit c after RB-00 shows Docker Compose's behaviour.

**Affects:** `BBB_FEATURES`

### value-patterns

Each variable has a value pattern (OQ-23). Adopt the patterns, and how are they enforced?

- **(a)** Entrypoints call bbb_require_match with the contract pattern; a bad value stops the container naming the variable.
- **(b)** Only setup and preflight check the patterns; entrypoints check presence only.
- **(c)** Warn only.

**Recommendation:** a. Values are substituted verbatim into config files; the pattern is the injection guard, and setup/preflight reuse the same patterns.

**Affects:** `BBB_DOMAIN`, `BBB_PUBLIC_IPV4`, `BBB_SHARED_SECRET`, `TURN_SECRET`, `ACME_EMAIL`, `BBB_FEATURES`

### env-vs-override-precedence

For node-config services (bbb-webhooks, bbb-webrtc-sfu) env variables beat Tier 3 files, the reverse of "override files win" elsewhere. Accept and document, or make entrypoints skip env for keys present in the Tier 3 file?

- **(a)** Accept and document per component (the reference page lists it).
- **(b)** Entrypoints inspect the Tier 3 file with yq and do not export env for keys it sets.

**Recommendation:** a. Upstream behaviour, no extra logic in entrypoints.

**Affects:** `WEBHOOKS_BEARER_AUTH`
